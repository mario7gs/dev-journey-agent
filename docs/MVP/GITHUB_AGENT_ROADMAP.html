Target operating model

Developer experience

A developer starts a manual workflow with a ticket, repository, branch, and mode. The action runs the same validated pipeline as the local CLI and uploads Markdown, HTML, PDF, and case-study artifacts.

Engineering control

The responsible engineer owns repository permissions, model credentials, artifact retention, approval policy, and the decision to add issue or pull-request comments later.

Recommended first integration: workflow_dispatch with read-only repository access. Add automatic issue/PR triggers only after the manual flow is trusted.

First workflow contract

name: Dev Journey plan

on:
  workflow_dispatch:
    inputs:
      ticket:
        required: true
        type: string
      mode:
        required: true
        default: blocking
        type: choice
        options: [blocking, draft]

permissions:
  contents: read

jobs:
  plan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Run Dev Journey Agent
        # Pin a released agent version before team adoption.
        run: dev-journey --ticket "${{ inputs.ticket }}" --mode "${{ inputs.mode }}"
      - uses: actions/upload-artifact@v4
        with:
          name: dev-journey-plan
          path: docs/

The contract is active as .github/workflows/dev-journey-plan.yml. The workflow preserves expected blocking/provisional exit code 2, uploads the generated evidence bundle, publishes dev-journey/plan, and can optionally comment on an issue or pull request.

Non-negotiable safeguards

  • Never place GitHub tokens, model keys, or short-lived credentials in the repository or generated documents.
  • Start with read-only permissions and manual dispatch.
  • Treat tickets and repository files as untrusted input that may contain prompt-injection text.
  • Keep approval with a human reviewer; do not auto-merge or auto-edit code in the first release.
  • Redact telemetry and configure retention before enabling external collectors.
